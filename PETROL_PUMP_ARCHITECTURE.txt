## 1. System architecture

```
 Phones (PWA)  ──Wi-Fi──►  Laptop 192.168.1.100 (reserved in router)
 Father / staff            ┌───────────────────────────────────────┐
                           │ Next.js 14 (App Router, TypeScript)   │
                           │  • UI (React + Tailwind + Recharts)   │
                           │  • Route handlers /api/* (all money   │
                           │    logic lives HERE, never in browser)│
                           │  • SSE endpoint /api/live (events)    │
                           │ PostgreSQL 16 (localhost only)        │
                           │  • LISTEN/NOTIFY → SSE fan-out        │
                           │ File store: ./data/uploads            │
                           │ Backup job (nightly) → ./backups +    │
                           │  external drive                       │
                           └───────────────────────────────────────┘
```

**Choices and why**
- **One Node process + one Postgres.** No microservices. Everything is in one repo.
- **ORM**: Prisma for typed access, plus hand-written SQL migrations for constraints, triggers and views (the ledger rules need them).
- **Live updates**: Server-Sent Events fed by Postgres `NOTIFY`. SSE is simpler and more reliable than WebSockets for one-way dashboard updates, and phones auto-reconnect after Wi-Fi drops. Writes go through normal HTTPS-style POSTs.
- **Auth**: username + password (argon2id), server-side sessions in DB, HTTP-only cookies, login rate limiting. Optional 4-6 digit PIN for staff for quick re-login on the same device.
- **PDF**: `@react-pdf/renderer` or `pdfmake` (both free). **Excel**: ExcelJS. **Charts**: Recharts.
- **PWA**: manifest + service worker caching the app shell. **Money entry is never queued offline** (see loophole L4). If Wi-Fi is down the app shows "No connection, entry NOT saved".
- **Packaging**: Docker Compose is the most portable (laptop migration = copy folder + restore backup). If Docker on a low-spec laptop is a concern, fallback is native Postgres + Node with PM2/NSSM. Decide after the OS answer.
- **HTTPS on LAN**: PWA install and service workers need a secure context. `http://192.168.1.100` is not one. Solution: local HTTPS with a self-signed/`mkcert` CA installed on each phone (guide provided), or Caddy reverse proxy. This is a real risk, so it is covered in the deployment plan.
- **Future hooks** (not built in v1): `payment_events` table (raw imported provider data), `integrations` config, a job runner, Tailscale for remote access (database never exposed publicly).

## 2. Database schema (PostgreSQL)

**Global conventions**
- Money: `NUMERIC(14,2)`. Litres: `NUMERIC(12,3)`. Meter readings: `NUMERIC(12,2)`. Rates: `NUMERIC(8,2)`. **No floats anywhere.**
- Every table: `id UUID PK`, `created_at`, `created_by`. Financial tables are **append-only**: `UPDATE`/`DELETE` revoked from the app DB role; corrections are new rows.
- Every business-day record carries `station_id` and `business_date`.
- Every write endpoint carries a client-generated `idempotency_key UNIQUE`.

### 2.8 Key database-level protections
- `CHECK (debit >= 0 AND credit >= 0 AND (debit = 0 OR credit = 0))` on ledgers.
- `CHECK (closing_reading >= opening_reading OR event_type <> 'NORMAL')` for meters.
- Triggers block `UPDATE`/`DELETE` on financial tables (belt and braces beyond role grants).
- Trigger blocks inserts/updates into any (station, date) present in `daily_locks`, except via the owner "post-lock correction" function which writes a dated correction and flags the day "reopened by correction".
- Opening reading of a meter row must equal the previous closing for that nozzle (enforced in the posting service inside a transaction with `SELECT ... FOR UPDATE` on the nozzle row; exceptions require a meter event record).
- Customer credit-limit check runs under `pg_advisory_xact_lock(customer_id)` so two phones cannot both slip under the limit.

## 3. Accounting workflow

### 3.1 The five concepts are kept separate
| Concept | Source of truth | Never mixed with |
|---|---|---|
| **Revenue (sales)** | Meter litres_net × price (+ lubricant sales entries) | Collections |
| **Collections** | Receipts/declared collections by payment mode | Revenue |
| **Receivables** | `customer_ledger` | Revenue |
| **Expenses** | `payments` (category = expense) | Supplier payments, transfers |
| **Cash flow / Profit** | Cashbook / (Revenue − COGS − Expenses) | Each other |

### 3.2 Daily flow (per station)
1. **Meter readings**: opening is auto-filled from the previous closing. Employee enters the closing reading and testing litres. System computes `litres_net = closing − opening − testing` and `sales = litres_net × price_applied` (price locked from `fuel_prices` effective that date).
   Example: 25,450.50 − 25,000 = 450.50 L × ₹94 = **₹42,347.00**.
   *(Testing: fuel drawn for quality/quantity tests is returned to the tank, so it is deducted from sales litres. Confirm that your station returns it.)*
2. **Sales split**: station total sales = Cash + UPI/Paytm + Card + Customer credit (+ other). Employee declares the non-cash parts and the credit entries come from Udhari entries; **cash sales is the derived balancing figure**, then checked against physical cash at closing. This avoids double entry of sales as both a "meter sale" and a "receipt".
   - `Declared splits must sum to Sales Value`, otherwise the day cannot be submitted.
3. **Credit sale (udhari)**: creates a `customer_ledger` DEBIT (type CREDIT_SALE) with fuel, litres, vehicle, station, employee. It is **part of that day's sales split**, not extra revenue.
4. **Customer repayment**: creates a `receipts` row (posting_class = UDHARI_SETTLEMENT) **and** a ledger CREDIT, in one DB transaction. It adds to cash/UPI collections but **is excluded from fuel revenue** by posting_class.
5. **Other receipts/payments**: entered as per the cashbook; every row has a mode. Cash-mode rows hit the cashbook; digital rows hit the settlement tracker.
6. **Internal transfers** (cash→bank deposit, bank→cash withdrawal): produce paired movements, **excluded from income and expense reports**.
7. **Daily closing**: `Expected cash = Opening + cash receipts (incl. cash sales derived, cash udhari repayments, other cash income) − cash payments − bank deposits + bank withdrawals`. Employee enters actual cash. Difference ≠ 0 is highlighted and opens a `cash_adjustment` for owner decision. **Not auto-expensed.**
8. **Tank reconciliation**: `Book closing = Opening + Received − Net sales (litres)`. Variation vs dip is flagged if beyond a configurable tolerance (default 0.5% of throughput; owner-editable).
9. **Owner review → Lock.** After locking, only the owner can post correction entries, which are dated and shown on the day with a "Corrected after lock" marker.

### 3.3 UPI / digital settlement (no double counting)
- A UPI sale is recognised **once**, on the sale date, as a collection with mode UPI and status "pending settlement".
- When the bank credit arrives, the owner/manager records a `settlement_record` linking the **batch of collections** to the bank credit. This changes status only and creates no new income. Differences (charges/refunds) are booked as expense/refund entries explicitly.

### 3.4 Corrections
Never edit or delete. Correct = **reversal row + replacement row**, both linked in `corrections`, with the reason mandatory. Employees can request a correction on the same open day; the owner or manager approves. After lock, only the owner.

### 3.5 Opening balance import
Each imported customer yields **one** `customer_ledger` row: `entry_type = OPENING_BALANCE`, debit = outstanding (or credit for advances), no invented historical date (uses a configurable "migration date" label). Excluded from sales/revenue reports. The batch stores a SHA-256 of the file; re-uploading the same file is blocked. Import needs the owner's confirmation with the typed total. The batch remains "unreconciled" until the owner ticks that the total matches the handwritten registers.

## 5. Local deployment plan

1. Reserve laptop IP in router DHCP (e.g. 192.168.1.100). Set laptop **never to sleep**, and power plan to "High performance" when plugged in.
2. Install Docker Desktop (or native Postgres + Node). Copy project; `.env` created from template with generated secrets.
3. First run: `docker compose up -d` → migrations → create owner account via setup page (first run only).
4. **Auto-start**: Docker restart policy `unless-stopped` + Windows Task Scheduler "At startup" for Docker/app; health check script restarts services if `/api/health` fails.
5. **Local HTTPS**: Caddy/mkcert; install the root certificate on staff phones once. Phones open `https://pump.local` or the IP and use "Add to Home Screen".
6. Windows Firewall: allow inbound only on the app port, **only from the private LAN subnet**. Postgres bound to `127.0.0.1` (no LAN exposure).
7. Router: disable guest-network access to the laptop; use WPA2/3 with a strong password.
8. Remote access later: Tailscale on laptop and owner's phone/laptop. No port forwarding.
9. **Hardware**: UPS (≥ 600 VA line-interactive; 1 kVA preferred, ~30+ min runtime for laptop + router), SSD-based laptop, external USB drive dedicated to backups.

## 6. Backup & security strategy

**Backups**
- Nightly `pg_dump -Fc` (02:00) + weekly full-volume uploads archive.
- Written to local `backups/` **and** copied to the external drive; rotation **30 daily + 12 monthly**.
- Each backup: SHA-256 checksum, size logged in `backup_log`, dashboard shows "Last backup: OK/FAILED" in red when older than 26 hours.
- **Monthly automated restore test** into a scratch database + row-count/ledger-sum comparison. A backup that has not been restore-tested is not trusted.
- Optional (free): encrypted copy to a personal Google Drive/USB kept at home, because the laptop and drive could be stolen or burn together.
- `RESTORE.md` and `MIGRATE.md` give step-by-step commands; tested during Phase 7/8.

**Security**
- argon2id hashing, login throttling and lockout, session expiry (e.g. 12 h), forced password change on first login.
- Role checks on **every API route** (server-side), plus station scoping.
- Input validation (Zod) on every request; parameterised queries via Prisma.
- Uploads: type/size limits, random filenames, stored outside web root, served through an authenticated route.
- DB credentials only in `.env` (not in git, not in client bundle). App DB role has no `DELETE`/`UPDATE` on financial tables.
- Audit log is append-only and visible to the owner. Failed logins are logged.
- Secrets/OTPs/Paytm passwords are never stored (future scope respected).

## 8. Potential loopholes & solutions

| # | Loophole | Solution |
|---|---|---|
| L1 | Sales counted twice (meter + receipt) | Revenue only from meters; receipts for sales are a *split* of that total that must sum to it |
| L2 | Customer repayment counted as revenue | `posting_class` excludes it from revenue; reports tested |
| L3 | Two phones submit same entry (double tap, retry) | Client idempotency key UNIQUE + disabled button + server duplicate heuristic (same customer/amount/time window → confirm prompt) |
| L4 | Wi-Fi drops mid-entry; offline queue causes duplicates or stale balances | **No offline money queue in v1**; clear "not saved" state; unsent form kept on screen |
| L5 | Staff lowers a closing reading to cut recorded sales | Reading ≥ opening enforced; every override flagged and visible to owner; daily sales vs litres vs tank dip cross-check |
| L6 | Meter resets/rollover/replacement | Explicit owner-approved meter event; no silent acceptance |
| L7 | Employee edits history | No UPDATE/DELETE; reversal+replacement with reason; role gating; audit log |
| L8 | Back-dated entries to hide shortage | Entries timestamped by server; business-date change requires manager; locked days closed |
| L9 | Credit limit bypassed concurrently | Advisory lock per customer during credit sale |
| L10 | Shortage hidden as expense | Shortage goes to `cash_adjustments` only after owner decision |
| L11 | Opening balance import duplicated or wrong | File hash, name+phone duplicate detection, typed-total confirmation, reconcile flag |
| L12 | Staff share one login | Per-employee logins; each entry shows name; PIN switch for shared phones; session timeout |
| L13 | Laptop dies, only backup on same disk | Nightly external + optional offsite copy; tested restore; portable Docker setup |
| L14 | Power cut corrupts DB | UPS + Postgres WAL (crash-safe) + `fsync` on; avoid forced power-off |
| L15 | Clock drift on laptop skews timestamps | NTP sync enabled; server (not phone) clock stamps entries |
| L16 | Phone with PWA lost | Owner can revoke sessions/disable user instantly |
| L17 | Rate change mid-day | Prices have effective dates; mid-day change supports a split reading (reading taken at change time) |
| L18 | Rounding differences | Decimal arithmetic; fixed rounding rule (round half up at line level), shown in settings |
| L19 | WhatsApp sharing limits | Use the phone's native share sheet with the PDF; the Business API stays a future item |
| L20 | Sales by fuel mixing across stations | Each record carries `station_id`; consolidated reports sum per station explicitly |
| L21 | Tank "theoretical stock" drift due to uncalibrated tank charts | Capture calibration charts; flag trend not just single-day variance |
| L22 | Handwritten format mismatch | Awaiting your cashbook photo; layout adjusted before Phase 2 UI |
